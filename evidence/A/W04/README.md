## What this dossier proves

- The W04 control mechanism refuses to energize: output stage compiled out, all
  seven limits `UNRESOLVED`, adapter rejects every enable, proven by static
  contracts plus a 34-scenario host harness against the real control core.
- One conservative H6 energization really happened, with valid 1 Hz PZEM
  electrical samples and an automatic 60.000 s stop.
- Across 132 ROM banners deduplicated to 116 unique start events, no start ever
  produced an unintended output state and all seven production resets came up
  SAFE_OFF — but no start was ever a genuine power-on, which is why A-W04-04 is
  not closed.
- The delivered bytes compile with ESP-IDF v6.1, and every source file in that
  build is hash-pinned.

The committed raw captures contain seven per-boot console authorization tokens
(`#CG AUTH token=…`). Each is generated by `esp_random()` at boot, lives 120 s,
cannot be used in another boot and cannot energize the delivered firmware, so
they are inert; they are listed here so a reviewer does not mistake them for
credentials.

## What it does not prove

- Cooling performance from the delivered code, a safe operating envelope, a
  continuous TEC rating, or W04/H4/H5/H6 completion — see `acceptance.md` §1–§4.
- Anything about H7/H8 as W04 evidence: those trees are later-week work, left
  local, recorded by aggregate digest only (`ARTIFACT-MANIFEST.md` §2.3). The
  600 s cooling figures are reproduced here as cross-week measurements at
  **100 % duty**, not as a conservative W04 response.
- The operator statements of 2026-11-02 (fuse installed, 1.75 mm² conductor,
  probe placements) are photographs or measurements. They are statements until
  the images exist.
