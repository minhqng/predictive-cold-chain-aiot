## 3. Defects found and fixed while building W06

1. **`split_line()` never assigned `*verb` on the two-token path** in the
   delivered W04 parser, so `ARM`/`CLEAR`/`START`/`RUN`/`PHASE` compared
   uninitialized stack memory — undefined behaviour that no test had ever
   exercised. Found by the first host parse of those verbs in this slice; fixed,
   pinned by a scenario and by a static check, and a mutation removes the fix
   again to prove both fail.
2. **Five checker assertions could not fail** when their mutation tests were
   first run: the unsynchronized guard, the duplicate branch and the
   overflow-refusal branch each passed on a string that survived being made dead
   code; `nvs` was checked in the wrong file; and the ACK status-name function was
   only checked for containing the seven names, not for containing **only** them
   (a `VERIFIED` status would have passed). All five rewritten to bind the live
   construct, then re-proved.
3. **The demo trace initially reported a phantom replay** because two unrelated
   fixtures shared a `command_id`, which is the aggregation key. Distinct ids
   restored a truthful demo; the lesson is recorded, since a trace keyed on
   command identity must not merge unrelated submissions.
4. **Serial schema 3 vs command schema 1 collision risk**: the ACK line states
   `schema=1` for the docs/02 envelope while the telemetry line says `schema=3`;
   a test asserts the ACK never carries the serial number, so the two streams
   cannot be conflated by a reader or a parser.
5. **The trace tool paired rows with records positionally.** Report rows are
   sorted by `command_id` while parsing keeps arrival order, so `--per-frame`
   attached the wrong telemetry frames to the wrong command whenever the two
   orders disagreed — and they agreed by luck on the demo fixture, whose ids are
   already ascending. Found by the post-fix review, now looked up by identity and
   pinned by a test that feeds the ids in the opposite order. See
   `physical-command-trace.md` §3.1.
6. **A pre-identity rejection could overwrite a remembered canonical result.** The
   wrong-device and unsupported-schema branches stored their verdict under the
   submitted `command_id`, so a malformed or foreign-addressed replay of an
   already-accepted id replaced the canonical answer the store held. Rejections
   that happen before the record is established as this device's command are no
   longer stored, and a scenario plus a mutation-pinned check keep them out of the
   store. Unreachable on the shipped board (one device id, no transport), but the
   rule is the contract's, not the configuration's.
7. **The local-test distinction rested on a missing field.** A `LOCAL_CONSOLE`
   record was refused because it carries no expiry — true today, and one change to
   the bridge or the clock would have made it false. `cg_command_validate` now
   refuses it explicitly, and the rule is now stated as "only the canonical
   network source is admitted" rather than as a prohibition on one named
   alternative; §3.8-§3.10 below record what the correction pass found next.

8. **The ACK omitted `device_id`.** docs/02 §32.3 lists `device_id` as ACK payload
   (line 2206) and `handoff-w06.md` documented it in the payload table - but the
   formatter never emitted it, so the handoff described bytes the firmware did not
   produce. The field now comes from the device's own context, never from the
   command's `device_id`: echoing a requested identity would be evidence of a name,
   not of who answered. Worst case re-measured at 592 bytes, budget raised to 768.
9. **An incomplete record became an implicit command.** `cg_command_parse_fields`
   required only `schema_version`, `device_id` and `command_id`, then `memset` the
   rest. Because `CG_CMD_COOLING_OFF = 0`, a record with no `action_cooling` parsed
   as a valid order to stay off, and one with no policy provenance or reason still
   reached the validator. Every §28.2 mandatory field is now required by name with
   its own reason token, `controller_id` stays optional per §28.3, and a field named
   twice is refused rather than resolved by whichever copy the parser reached last.
10. **An unlabelled source could be accepted.** `CG_CMD_SOURCE_UNKNOWN` is the zero
    value, and the previous gate named only `LOCAL_CONSOLE`, so any record whose
    source was never stamped - which is what the parser produces - could reach
    `ACCEPTED` through absence of a prohibition. Validation now admits
    `CG_CMD_SOURCE_NETWORK` only, and does so *before* the store lookup, so an
    inadmissible source cannot read back the canonical result another path earned
    for the same `command_id` either. This classifies provenance; it does not
    authenticate it, and `source` is deliberately not a wire field.

## 4. Physical actions still owed

1. Time synchronization or a contract amendment, so `expires_at` becomes
   evaluable on the device (C's NTP/SNTP path, or a documented relative-expiry
   amendment). Until then **no remote command can be accepted at all** — which is
   safe, but should be a decided state, not a permanent accident.
2. A transport decision with C (no network stack exists in firmware and the W04
   checker proves it; adding one is its own safety-reviewed slice).
3. Authorized flash of this image, with the backup/restore prerequisites from the
   W05 record, then the reset-with-command power-cycle log.
4. Supervised energized session for `ELECTRICAL_VERIFIED`/`THERMAL_VERIFIED`.
5. W05's ≥30-minute telemetry capture remains open, unchanged by this slice.

## 7. Dated corrections to earlier records (2026-11-02)

The W04 and W05 dossiers are deliberately left byte-identical to the revision
that was reviewed, so these errors are corrected here instead of in place.

1. **Six operating limits, not seven.** `evidence/A/W04/README.md`,
   `evidence/A/W04/acceptance.md`, `evidence/A/W05/README.md` and
   `evidence/A/W05/acceptance.md` each say "seven". `CG_LIMIT_COUNT` is 6:
   `current_max_a`, `voltage_max_v`, `voltage_min_v`, `hot_side_max_c`,
   `duty_max_permille`, `on_time_max_ms` (`firmware/main/cg_tec_limits.h:23-31`).
   The fail-closed conclusion is unchanged — all six ship `UNRESOLVED` — so this
   is a wording defect, not a safety one.
2. **The W05 serial-line budget is superseded by schema 3.** W05 published 1873
   bytes typical, 2098 constructed worst case, 2560 shipped
   (`CG_TELEMETRY_LINE_MAX` then). The command and desired-state fields raise the
   measured worst case to 2256 bytes against a raised buffer of 3072
   (harness: `w06_worst_case_len=2256 budget=3072`). The new ACK line has its own
   measured budget: 592 worst against `CG_COMMAND_ACK_LINE_MAX 768` (W06 first
   shipped 558/640; adding the required ACK `device_id` field moved the worst case
   to 592, which is 92 % of 640 and inside the buffer but outside the 10 % margin

   estimate built on the W05 frame size understates W06 - by 158 bytes worst to
   worst (2256 against 2098), or 383 if a W05 typical frame is compared to a W06
   worst case - and must be recomputed from these numbers, stating which basis it
   uses.
3. **Checked and *not* in error:** W05 §6 claimed thirteen files of the W04 pin
   list differ on its own branch. Re-counted from the delivered W05 head
   (`f249b77`) that number is correct — 13 — and the 16 above is W05's 13 plus
