# A-W06-05 — Physical command trace

docs/05A §15 asks, with Members C and D:

```text
backend command -> device accept -> applied -> PZEM -> thermal response
```

`firmware/tools/cg_command_trace.py` implements that chain as **five distinct
stages with promotion rules that refuse to guess**, and this file records what
evidence exists for each stage today.

**Nothing in this slice demonstrates a physical command round trip.** There is no
transport in this firmware, no backend issuer, no authorized energized session,
and the W06 build has never been flashed. The two JSON artifacts are therefore:
one that exercises the rules on emitted bytes, and one honest empty result over a
real capture.

## 1. Stage rules

| Stage | Promoted only when |
|---|---|
| `COMMAND_SEEN` | a `#CG CMDACK` line names the `command_id` |
| `DEVICE_ACK` | at least one ACK exists; more than one with no `DUPLICATE_CANONICAL` is flagged as an idempotency failure |
| `APPLIED_STATE` | the ACK was `ACCEPTED`/`DUPLICATE_CANONICAL` **and** a later telemetry frame reports `cooling_applied=ON` |
| `ELECTRICAL_VERIFIED` | such a frame also carries a fresh current reading ≥ 0.05 A |
| `THERMAL_VERIFIED` | ≥3 usable chamber-air readings in the attributed frames span ≥0.25 °C |

A blocked stage records `blocked_at` and the reason text; the tool never
back-fills a later stage from an earlier one, because `docs/02` §32.2 (2188-2198) says an
ACK is protocol evidence and not "the chamber cooled".

The two thresholds (0.05 A, 0.25 °C) are **named analysis floors** printed in the
report, not contract values: the PZEM LSB is 0.01 A and one DS18B20 LSB is
0.0625 °C, so both floors are above the noise floor of the instruments and below
any deliberate bench change. They are parameters to review with B and D, not
frozen requirements.

## 2. What the artifacts show

`trace-committed-w04-capture.json` — the real, committed W04 bench capture
(`evidence/A/W04/g1/40-g1-boot-60s.log`):

```text
verdict=NO_COMMAND_LINES_PRESENT  commands_observed=0  ack_lines=0
```

Correct and complete: that capture predates the command layer, so the honest
trace is empty. No lifecycle stage may be claimed from bytes that never carried a
command.

`trace-host-demo.json` — five synthetic commands built from ACK lines emitted by
the delivered formatter, plus the W05 fixture telemetry line:

| Command (last 4 chars of id) | ACK | Blocked at | Why |
|---|---|---|---|
| `000a` | `SAFETY_BLOCKED` | `DEVICE_ACK` | unsynchronized clock; expiry unverifiable |
| `000b` | `ACCEPTED` | `APPLIED_STATE` | accepted, but no following frame reported `cooling_applied=ON` |
| `000c` | `EXPIRED` | `DEVICE_ACK` | genuinely past expiry under an injected synchronized clock |
| `000d` | `REJECTED` | `DEVICE_ACK` | addressed to another `device_id` |
| `000e` | `DUPLICATE_CANONICAL` | `APPLIED_STATE` | replay answered the canonical verdict, applied never ON |

It is labelled `is_physical_measurement: false` in its own provenance block. Its
value is that the refusal logic is exercised on real bytes — including the case
that matters most: **an `ACCEPTED` command stops at `APPLIED_STATE`,** which is
exactly what must not be silently upgraded to "cooled".

`demo-command-capture.log` is the input, generated by the same script.

## 3. Reproduce

```bash
py evidence/A/W06/build_contract_artifacts.py --check
py firmware/tools/cg_command_trace.py evidence/A/W06/demo-command-capture.log --per-frame
py firmware/tools/cg_command_trace.py evidence/A/W04/g1/40-g1-boot-60s.log
```

## 4. What a real trace requires (NEED_USER_ACTION, in order)

1. **An issuer.** Member C's backend must publish a command. Until then no
   physical trace can exist at all, because the device has nothing to receive.
2. **A transport decision, and it is C's.** This firmware deliberately has no
   network stack and `cg_check_firmware_w04.py` proves it. Adding MQTT belongs to
   a Member A/Member C integration slice with its own safety review, not to W06.
3. **An authorized flash** of the current image, with the full backup/restore
   prerequisites (installed image identified, backup verified, target hashes
   verified, restoration procedure written down, TEC branch isolated).
4. **An authorized, supervised energized session** with a stated current and
   temperature ceiling and the hot-side fan confirmed, to produce
   `cooling_applied=ON` with real PZEM current.
5. Only then can the trace reach `ELECTRICAL_VERIFIED` and `THERMAL_VERIFIED`,
   and only with Member D's policy in the loop can `ACCEPTED` mean anything about
   a control action.

## 5. Relationship to A-W06-06

`reset-command-log.jsonl` records the host scenario: accepted before the reset,
and after the reset the same id is not remembered (`duplicate_recognized=0`), is
re-validated against a fresh boot's unresolved limits (`OUT_OF_RANGE`), and the
applied state is `OFF`. The physical half — actually power-cycling a board that
has just been commanded ON and proving nothing resumes — requires the flash in
step 3 and is not claimed here. It is also weakly bounded by existing evidence:
the W04 record shows 7 verified production resets each starting
`tec_state=OFF output_stage=DISABLED pwm_duty=0`, which is why "a reboot does not
resume actuation" is a claim about the *compiled-out* stage today, and a test
still owed once a stage exists.
