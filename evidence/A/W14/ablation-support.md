# W14 logical ablation support (A-W14-02)

Generated by `evidence/A/W14/build_w14_artifacts.py` from committed captures.

docs/05A A-W14-02 is explicit: do **not** unplug T2/T3 for core A1. The ablation is logical - Member B selects one sensor feature set versus the three-sensor set from the **same physical runs**, which is what keeps the comparison physical-condition-controlled instead of run-to-run. This file produces those datasets.

## How the control is checked, and what it does not prove on its own

Every variant below is computed over the same rows of one capture (`evidence/A/W04/tec-cooling-response-600s.csv`, 957 rows, boot `56044b74`). The conditioning columns `['device_ms', 'state', 'pwm_applied_permille', 'door_open', 'boot_id']` hash to the capture-wide `d1671cc668ca0fa1`, and that value is stamped on every variant-phase row of the capture.

Read the stamp for what it is: one hash per capture, so the stamped rows cannot disagree with each other and cannot, on their own, prove that the variants walked the same physical rows. The falsifiable part of the control is `physical_condition_control`: the fingerprint of the rows each variant actually used, per phase - here `{'baseline': ['3f548d3e09f4d95a'], 'cooling': ['8512f2f8a65e3c77'], 'recovery': ['cfab6ca2eabf9ef5'], 'undetermined': []}` - plus `one_fingerprint_per_capture` (`True`), which is computed from those sets and is False the moment any phase's usable variants used different condition rows.

What makes it a proof rather than a label is that none of it is trusted: `validate_w14.py` re-reads the committed capture, re-computes the fingerprint and re-derives every `ablation-support.csv` row's `device_ms` to `feature_c`/`pwm`/`door`/`boot_id` attribution from the source rows. A fingerprint, attribution or feature value the capture does not produce fails the dossier, so the check is the recomputation, not this sentence.

## Per-sample series for Member B

`ablation-support.csv` is long-format: one row per variant per sample, carrying `capture`, `boot_id`, `phase`, `variant`, `feature_terms`, `feature_roles`, `is_chamber_air`, `includes_hot_side`, `device_ms`, the commanded duty, the door token and the conditioning fingerprint. A join on `device_ms` inside one `conditioning_fingerprint` gives B feature sets from the same physical instant - and the validator re-derives each of those rows from the capture it names, so the join keys are checked against the source rather than taken on trust.

## What this is not

- it is not two runs compared: it is one run described several ways, which is the point (physical conditions held), and it therefore carries no run-to-run information
- it is not a calibration: `evidence/A/W02/sensor-consistency.csv` is a bench session whose probe positions were not yet frozen and is not a spatial input here
- it is not a disturbance test: no door-open event exists in committed data
